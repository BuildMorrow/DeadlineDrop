## Google Calendar import — 2026-11-06

An ICS file generated by DeadlineDrop's actual extraction and export functions using synthetic inputs was imported into a separate test calendar in Google Calendar. Google reported 4 of 4 imported. The calendar was read back with its Asia/Ho_Chi_Minh timezone: the all-day event was on May 20, 2027; a timed event began May 21 at 14:30; a range on May 22 ran from 10:00 to 11:00; and May 23 at 14:30 UTC appeared at 21:30 local. Titles matched. For the two timed events with no end in the ICS, Google assigned a one-hour end time. This application warns users to check durations after importing. This is one calendar client, not evidence for other clients; the file was generated directly by the application functions, not downloaded through the UI.

Record actual results and browser, operating system, timezone, and calendar application before release. Browser checks below used the in-app browser on Windows with timezone Asia/Saigon; other cases are **Not run** unless explicitly recorded. Do not use private information in examples.

## Automated calendar parser check

The Vitest interoperability test parses generated all-day, timed and ranged events using `ical.js`, including Unicode and escaped text. This is a structural parser check, not evidence of importing into Google Calendar, Outlook or any other calendar application.

The automated axe-core check covers the initial page and an unresolved range in jsdom. Color contrast is disabled because jsdom does not render a real page; this check cannot establish visual contrast, screen-reader behavior, physical-device usability, or full WCAG conformance.

## Keyboard range resolution — 2026-11-05

In-app browser on Windows, timezone Asia/Saigon. Using the keyboard, the skip link moved focus to the input; after entering `Deadline 2027-05-20 10:00-11:00`, navigating to Find dates, and choosing Use as a time range, focus moved to Confirm event 1 after the fix. Before the fix focus returned to the page because the resolution control was removed. An automated interaction test also checks confirmation and that editing invalidates it. This is one keyboard path, not a complete screen-reader or physical-device audit.

## Responsive content and sampled contrast — 2026-11-06

On Windows in the in-app browser, with a 320 × 720 viewport override, both a long Vietnamese sentence and an 800-character unbroken synthetic title produced a review card without document-level horizontal overflow (measured document and viewport widths were both 305 CSS pixels). This is a simulated viewport, not a physical device test.

Foreground and nearest opaque background colors were read from the rendered page and WCAG contrast ratios calculated for a sample of text: heading 16.04:1, hero body 10.08:1, field label 9.18:1, input 16.16:1, hovered primary button 11.20:1, bottom note 9.48:1, source text 10.49:1 and event details 9.16:1. These sampled values exceed 4.5:1; they do not constitute a complete contrast audit of every state or a screen-reader test. Full keyboard and assistive-technology checks remain outstanding.

## Keyboard confirmation and export — 2026-11-06

In-app browser on Windows, Asia/Saigon. Keyboard-only: Tab to the skip link, Enter, type `Workshop 2027-05-20 10:00-11:00`, Tab to Find dates and activate, navigate to Use as a time range, activate, then confirm. Before the fix, confirmation disabled its focused button and focus fell to the document. After the fix, the confirmed button retained focus, exposed its disabled state through `aria-disabled`, and Tab moved to Export .ics; Enter activated export. The browser reported no visible error, but the downloaded file was not independently inspected in this run. This is a tested path, not a screen-reader audit or a guarantee for every keyboard workflow.
